# 客户购买恢复：实现和验收

范围：商业 PRD P0-03 的客户端幂等与购买恢复体验；不是正式支付 SDK 或真实收款验收。

## 本次实现

- 首次购买在外发前产生并显示请求编号，同一页面的同一次购买重试保留编号和 SKU。并发点击被禁用；更换 SKU 必须明确开始另一笔购买。
- 25 秒客户端等待上限；超时或响应丢失后保留原编号，不自动重试，不声称支付未发生。
- `POST /billing/checkout/lookup`：网页登录态 + 原 `Idempotency-Key`；只读本客户冻结订单，即使套餐变化或支付适配器禁用仍可查询。
- `GET /billing/topups/{order_id}`：本客户订单状态、现金最小单位、服务额度与下一步；其他客户和无会话访问被拒绝。
- 仅 pending 且合法无嵌入凭据的 HTTPS 链接可展示“继续原订单支付”。创建中、待对账、已付、退款状态不自动跳转。
- 订单列表显示完整订单号，提供查询/恢复与刷新余额；付款页面返回后重新登录，再从列表查原订单。页面返回绝不触发入账。
- 请求编号和会话仅存在内存；不持久化支付链接、Key 或登录令牌。退出清空恢复区；旧会话迟到结果不能重新显示支付链接。
- 非生产环境显式标明测试/模拟支付；现金金额标明最小货币单位，不把 cents/minor units 直接当作 dollars。

`checkout.js` 是同源 ES module，只有购买状态与 HTTPS 链接检查，不自行联网、不读取凭据、不执行持久化。控制台主脚本仍将令牌放在局部闭包中，并在 CAPTCHA 加载前移除一次性链接片段。

## 证据

本地全量：395 项 Python 测试通过，分支覆盖率 82%；TypeScript 类型检查与 41 项测试通过。一项既有 Starlette/httpx 弃用警告。`git diff --check` 通过。

- 新增 API 回归：反复查询不创建支付、不入账；租户隔离；支付禁用/套餐变化后仍能读冻结快照；不确定/已付状态不重建；无效编号、未知订单与危险链接拒绝。
- 新增前端单元测试：响应丢失后稳定编号/冻结 SKU；重复点击和在途清除拒绝；退出后迟到结果失效；查询不创建订单；只有 pending HTTPS 链接可恢复。
- 本地隔离 Chromium 390×844 实际操作：登录 → 创建订单并故意丢弃响应 → 使用原编号再次提交 → 上游假适配器仅创建一次支付会话 → 查询 → 合成已验证回调入账 → 付款链接消失 → 刷新后重新登录 → 按订单恢复 → 退出清理。无页面脚本错误、无横向溢出。
- 截图：忽略目录 `release-artifacts/checkout-recovery-mobile.png`。这是模拟测试，不是真实商户、用户或公网支付证据。

## 重复执行

以下只对本地可丢弃夹具执行。夹具固定监听 `127.0.0.1:8796`，结束进程即清理临时数据库；不允许部署夹具。

```bash
# 终端一：项目测试依赖已安装时
.venv/bin/python tests-browser/checkout_fixture.py

# 终端二：需要已安装且可解析的 Playwright 与 Chromium
node tests-browser/checkout.cjs

# 回归
.venv/bin/coverage run -m pytest -q
.venv/bin/coverage report --fail-under=80
npm run check
```

浏览器验证将 `https://gateway.example` 的请求全部转交本地夹具，保留业务请求与 HTTPS return_url；没有 DNS 请求或真实支付网站。夹具复用既有 managed 模式测试及假适配器，不放入生产镜像。Playwright 不加入运行时依赖，浏览器脚本未加入云端 CI；云端 CI 覆盖 Python、纯前端状态与既有构建/数据库门禁。

## 未完成和回滚

正式支付渠道/SDK、商户资格、真实回调与小额购买/退款仍未验收。现有控制台已有后续[英文/中文验收](CONSOLE-LOCALE-ACCEPTANCE.md)；完整运营后台与商业部署继续开发，不能因本记录而标记整站完成。

当前页面刷新不保留尚未到达服务器的编号；订单列表也可能暂时看不到在途请求，因此页面明确要求核对和等待，而非自动新购。需要更强的跨设备恢复体验时，必须单独定义不保存凭据的持久化策略。

本次只增加查询接口和前端状态，无数据库迁移。发生预发布回归时回退应用版本，保留订单、账本和在途状态；回滚不等于取消已经建立的支付订单。本轮没有生产部署、账号变更、真实支付或数据库迁移。
